# PITON V5: границы доверия и эксплуатация API

## Что хранит и проверяет сервер

Один обработчик `packages/server/handler.ts` принимает стандартный `Request` и возвращает `Response`. Его граф импортов не содержит `node:*`. Локальный Node API подключает отдельные SQLite/scrypt адаптеры, а маршрут `app/api/v1/[...path]/route.ts` подключает D1 и доверенную идентичность Sites. Контракт описан в `docs/API.openapi.json`; типы интерфейса находятся в `packages/contracts/index.ts`.

Сервер владеет учётными записями, профилями, XP ledger, попытками, свидетельствами освоения навыков, очередью повторений, сюжетными флагами, черновиками, проектами и их версиями. Эти данные не восстанавливаются из `localStorage` и не принимаются как готовый итог из браузера. Для доступа к приватным данным сервер каждый раз проверяет связь `profile.user_id` с текущим владельцем. Ответ на попытку доступа к чужому профилю или проекту — 404, без раскрытия существования чужих данных.

### Честная граница проверки Python

В этой версии Python реально исполняется в браузерной среде Pyodide. API принимает **публичное свидетельство `browser-preview`**, а не результат защищённого серверного grader. Тесты, решения и протокол доступны клиенту; технически подготовленный клиент может сконструировать ложное свидетельство. Эта версия подходит для учебного прогресса и самостоятельной практики, не заявляет защиту экзаменационных результатов, рейтингов с призами или сертификации.

API строго проверяет следующие свойства перед записью попытки:

- Владелец профиля, канонический ID урока, режим и ID варианта совпадают с текущим curriculum и контекстом запуска.
- `contentVersion`, `assessmentVersion`, `context.testsVersion` и обе версии runtime актуальны. Текущая среда — `pyodide-314.0.7`, протокол — `1`.
- Это `operation: "check"`, финальная фаза `complete` и `gradingAuthority: "browser-preview"`.
- Список результатов содержит **ровно все** актуальные ID тестов выбранного варианта, без пропусков, добавлений и дубликатов.
- Для зачёта нужны общий `status: "ok"`, отсутствие общей ошибки и `passed: true` вместе со `status: "ok"` у каждого теста. Успешный статус выполнения сам по себе не означает прохождение теста.
- Усечённый stdout, поток игровых событий или набор файлов не принимаются как успешный результат. Усечение необязательной отладочной трассы не отменяет проверку.

Некорректная структура или устаревшее свидетельство не создают попытку. Корректно оформленная неудачная проверка записывает попытку и учебное свидетельство без XP. Сервер не выполняет отправленный Python, не вызывает `eval` и не записывает пользовательские файлы в файловую систему машины.

`draftVersion` является версией редакторского контекста. Браузерный runtime отбрасывает устаревшие ответы при изменении контекста; API проверяет тип этого поля и остальные идентификаторы, но не связывает этот счётчик с номером серверного черновика. CAS-ревизия сохранённого черновика — отдельный механизм. В P0 нет криптографической привязки исходного кода к браузерному свидетельству.

## Вход и сессии

### Локальный Node

Standalone API всегда запускает handler с `authMode: "local"`. Он **игнорирует** заголовки `oai-authenticated-user-*` и любой переданный `trustedUser` в локальном режиме. Доверенный внешний вход существует только в hosted-адаптере.

Пароль имеет длину 10–256 символов при регистрации. Сервер использует scrypt с `N=32768`, `r=8`, `p=1`, случайной солью 32 байта и производным ключом 64 байта. В БД сохраняются параметры, соль и хеш, а не пароль. Сравнение ключей использует `timingSafeEqual`. Для неизвестного email выполняется тот же scrypt, а сообщение о неверном входе не различает отсутствующий адрес и неправильный пароль.

Сессия — случайный токен 32 байта. БД хранит только его SHA-256. Cookie `piton_session` имеет `HttpOnly`, `SameSite=Lax`, `Path=/`, срок 30 дней; на HTTPS добавляется `Secure`. После входа токен обновляется. Регистрация текущего гостя повышает **того же владельца** до локальной учётной записи, сохраняет ID всех профилей, XP и работы, затем отзывает все его прежние сессии. Уникальные ограничения идентичностей не позволяют двум параллельным регистрациям прикрепить разные локальные логины к одному гостю.

Каждый вызов локального `POST /auth/demo` создаёт нового UUID-владельца и три **его собственных** профиля Аня / Марк / Лера с нулевым прогрессом. Глобального общего демопрофиля нет. У новой обычной регистрации без гостевой сессии создаётся один профиль.

### Hosted Sites

Hosted route получает пользователя через supplied `app/chatgpt-auth.ts` и передаёт его в handler как `trustedUser`. Это доверие допустимо только за инфраструктурой Sites, которая аутентифицирует и выставляет указанные заголовки. Произвольный HTTP сервер с открытыми клиенту `oai-*` заголовками не является эквивалентом этого адаптера.

Связь хранится по уникальной паре `provider + subject`, а не по email. Одинаковый email у разных внешних идентичностей не объединяет их владельцев. Первый вход создаёт три личных профиля. Детерминированные ID для этого начального связывания позволяют параллельным первым запросам создать одну учётную запись и ровно три профиля.

На **каждом** hosted-запросе проверяется доверенная идентичность. Cookie без неё недостаточно; при смене внешнего пользователя старая прикладная сессия не открывает прежние данные. `auth/me` возвращает `authMode: "platform"`. Локальные login/register в этом режиме отключены; пароль для ChatGPT-входа не нужен. `auth/logout` отзывает прикладной токен, а полный выход из внешнего аккаунта выполняется ссылкой выхода Sites.

При размещении сайта в стороннем iframe необходимо проверить политику cookie среды. Текущая конфигурация использует `SameSite=Lax`; среда, не передающая такой cookie из iframe, потребует открывать приложение как верхнюю страницу либо согласовать инфраструктурную cookie-политику. Это эксплуатационная проверка hosted-preview, не основание ослаблять проверку Origin или доверие к внешнему пользователю.

## Запись, Origin и CSRF

Каждый изменяющий запрос требует заголовок `Origin`, совпадающий с разрешённым адресом приложения. `Sec-Fetch-Site: cross-site` отклоняется. Browser fetch отправляет Origin сам; тестовый Node `Request` задаёт его явно.

Все авторизованные изменения дополнительно требуют `X-CSRF-Token` из последнего `auth/me`. Токен вычисляется из случайного сессионного секрета с доменным префиксом и не сохраняется в БД открытым текстом. Вход, регистрация и открытие гостя не требуют прежнего CSRF-токена, но сохраняют проверку Origin. Cookie недоступен JavaScript; CSRF-токен предназначен для клиентского запроса.

JSON-запрос ограничен 2 МиБ. Поток ограничивается во время чтения, независимо от `Content-Length`. До рекурсивной валидации проверяются глубина (до 40) и число узлов (до 40 000). Zod-схемы отклоняют неизвестные поля, неверные перечисления, слишком большой код/файлы и небезопасные пути файлов. SQL использует параметры; пользовательские значения не подставляются в SQL-текст.

Rate limits находятся в БД и атомарно увеличиваются в фиксированном окне. Поэтому они действуют между запросами и изолятами, а не только внутри одного JS процесса. Используются отдельные лимиты для входа по адресу и email, регистрации, гостя, проверок, черновиков, проектов и tutor. При превышении API возвращает 429 и `Retry-After`.

| Операция | Лимит |
| --- | --- |
| Локальный вход по email | 8 попыток / 15 минут |
| Локальный вход по адресу подключения | 30 попыток / 15 минут |
| Регистрация по email / адресу | 4 / 10 за час |
| Новый гость по адресу | 10 за час |
| Проверки урока на профиль | 120 за час |
| Сохранения черновика на профиль | 600 за час |
| Создание / сохранение проекта | 30 / 180 за час на профиль |
| Tutor на профиль | 40 за час |

Node использует адрес сокета и не доверяет `X-Forwarded-For`. Hosted route использует доверенный subject для квот, где нужен идентификатор клиента. API возвращает `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` и ID запроса. Неожиданные ошибки скрывают внутренние сообщения и стеки; production hooks журналируют только ID запроса.

## XP, освоение, повторение и каталог

XP хранится отдельным ledger. Уникальное ограничение `(profile_id, lesson_id)` гарантирует одно начисление за канонический основной урок. Режим, повторная попытка, другая версия урока или другой idempotency key не повышают XP за тот же основной урок. Размер начисления берётся из curriculum.

Дополнительно уникальны `(profile_id, idempotency_key)` и `(profile_id, run_id)`. Повтор того же ключа с тем же нормализованным телом возвращает ранее записанную попытку с `duplicate: true`, `xpAwarded: 0`. Иное тело с тем же ключом или повторная запись того же запуска под новым ключом отклоняется. Вся запись попытки, XP и учебных свидетельств выполняется одной атомарной batch-транзакцией. Параллельные одинаковые запросы не создают частичных итогов.

Шкала навыка имеет уровни 0–4:

| Уровень | Основание в этой версии |
| --- | --- |
| 0 | Ещё нет свидетельств |
| 1 | Была проверяемая попытка |
| 2 | Есть успешная проверка с поддержкой либо без подтверждённой рефлексии |
| 3 | Успех без подсказок, изменённый исходный код и `reflectionCorrect: true` |
| 4 | Самостоятельный успех после наступления срока повторения и прежний самостоятельный успех в другом уроке или режиме |

Уровень подсказки учитывает как отправленный `hintLevel`, так и реальные обращения к tutor за последний час в том же профиле/уроке/режиме. Значения рефлексии и факт использования внешних подсказок остаются браузерными учебными свидетельствами, не защищённой аттестацией. Немедленный повтор не выдаёт уровень 4.

Неудачная практика назначает повторение через день. Успешная практика на уровне 2 — через 3 дня, уровне 3 — через 7 дней, уровне 4 — через 14 дней. Досрочная практика не отодвигает уже назначенный более ранний срок. `GET /progress` включает только наступившие повторения; `GET /progress/review` также возвращает полный `scheduled` список. Календарь серии активных дней использует `PITON_TIME_ZONE` (по умолчанию UTC).

`POST /progress/review` принимает `{profileId, skillId, submissionId}`. Он требует уже записанную успешную проверку этого навыка, выполненную после наступления срока и не старше суток. Этот endpoint только подтверждает выполненное действие: он не создаёт свидетельство и не начисляет XP за нажатие кнопки. Повторное подтверждение безопасно.

Prerequisites для опубликованных уроков применяются сервером. Исключение — полноценный демонстрационный `u5-l2`, доступный непосредственно из практики. Для него недостающие основы возвращаются как рекомендованные. Неопубликованные пункты каталога не выдаются за готовые уроки и не блокируют реальные цепочки готового контента. Завершение мира считается по опубликованным урокам, а `totalCount` сохраняет полный объём каталога. Самостоятельные готовые миссии сохраняются в drafts/projects, но не получают XP основного урока через `/submissions`.

## Черновики, проекты и экспорт

Черновик имеет ключ `(profile_id, lesson_id, mode)`. `PUT /drafts/:lessonId` требует `expectedRevision`: 0 создаёт первую версию, последующие записи должны совпадать с текущей. Конфликт возвращает 409 и актуальный черновик в `error.details.current`. Интерфейс может предложить сравнение, сохранив локально введённый текст.

Проект принадлежит профилю. Создание сохраняет ревизию 1. Каждое редактирование и восстановление требует `expectedRevision` и атомарно добавляет новую head-ревизию. Сохраняются последние **10 реальных снимков**, включая текущий. Восстановление старого снимка создаёт новый номер, не откатывает счётчик и не скрывает последующее изменение. Удаление проекта удаляет все его снимки. Одному профилю доступны до 100 проектов; одному владельцу — до 10 профилей. Конкурентные удаления не могут удалить последний профиль.

Пути файлов проекта — обычные относительные JSON-ключи. Запрещены `..`, `.`, абсолютные пути и пустые сегменты; до 32 уникальных файлов с суммарным UTF-8 содержимым 512 КиБ. Код ограничен 65 536 символами. API не исполняет эти файлы и не разрешает доступ к серверным путям.

`GET /profiles/:id/export` возвращает переносимый JSON выбранного собственного профиля: настройки, прогресс, черновики, проекты, их сохранённые ревизии, попытки, учебные свидетельства и ответы tutor. Пароли, хеши паролей, сессионные токены и внешние auth-identities не экспортируются. Экспорт профиля не является полной резервной копией учётной записи или базы.

## Tutor и данные для провайдера

Без провайдера приложение использует четыре подготовленных уровня помощи и возвращает `provider: "static"`. Отказ сети, превышение размера ответа или некорректный ответ провайдера также дают этот явный fallback. Уровень 4 требует `revealSolution: true`; UI должен показывать его как разбор решения.

Опциональный адаптер `createGenericTutorProvider` подключается только серверными переменными `TUTOR_ENDPOINT`, `TUTOR_API_KEY`, `TUTOR_MODEL`. Поддерживается совместимый JSON endpoint chat completions. Браузер не выбирает адрес, модель, секрет или system prompt. Endpoint требует HTTPS, кроме локального loopback; редиректы запрещены, время ожидания — 6 секунд, тело ответа ограничено 64 КиБ.

Провайдер получает ограниченный учебный контекст: режим, заголовок, цель, задание, утверждённую подсказку, текст теории и сообщение ученика. Email, ID владельца и профиля, сессия и прочие работы не отправляются. Поля исходного кода и ошибки добавляются только при **`shareCode: true`**. При `false` они игнорируются, даже если клиент всё же включил их в тело запроса. Пользовательский текст и код в prompt обозначаются учебными данными.

БД хранит ответ tutor, уровень, провайдера, факт согласия на код и числовые показатели usage. Отдельный transcript пользовательского кода или ошибки в tutor history не сохраняется. Ответы возвращаются только владельцу, максимум 50 последних, по профилю/уроку/режиму. Код может уже храниться отдельно в явно сохранённом черновике, проекте или попытке — это другой пользовательский объект. Текст провайдера остаётся недоверенным текстом для интерфейса и не должен рендериться через необработанный HTML.

## Node API, миграции и резервная копия

Проверенный Node runtime — 24.19.0. Entry point — `apps/api/server.ts`, CLI — `apps/api/db-cli.ts`. Стандартные команды:

```bash
node --import tsx apps/api/server.ts
node --import tsx apps/api/db-cli.ts migrate --db data/piton.sqlite
node --import tsx apps/api/db-cli.ts check --db data/piton.sqlite
node --import tsx apps/api/db-cli.ts backup --db data/piton.sqlite --to backups/piton-2026-10-18.sqlite
node --import tsx apps/api/db-cli.ts restore --from backups/piton-2026-10-18.sqlite --db data/recovered.sqlite
```

По умолчанию API слушает `127.0.0.1:8787`, использует `data/piton.sqlite` и обслуживает готовый `dist/standalone`. Настройки: `HOST`, `PORT`, `PITON_DB_PATH`, `PITON_STATIC_DIR`, `PITON_PUBLIC_ORIGIN`, `PITON_ALLOWED_ORIGINS`, `PITON_TIME_ZONE`. Для публичного адреса задаётся фактический HTTPS origin; конфигурация proxy должна сохранять соответствие маршрута и разрешённого Host. Сервер отклоняет неизвестный Host, не доверяет forwarded-заголовкам и ограничивает static-serving заданным каталогом после проверки реального пути. Dot-пути и выход через symlink за каталог не выдаются. Для неизвестного маршрута страницы используется SPA index; неизвестный файл возвращает 404.

Drizzle schema находится в `db/schema.ts`; SQL и snapshots создаются `drizzle-kit generate` в `drizzle/`. Sites применяет эти SQL-миграции к binding `DB`. Локальный CLI применяет тот же SQL по журналу и сохраняет SHA-256 каждого применённого файла; изменение старой применённой миграции вызывает ошибку. Повторный `migrate` безопасен. Node API выполняет миграции перед началом обслуживания.

Node SQLite включает foreign keys, WAL и busy timeout 5 секунд. Его `batch` делает `BEGIN IMMEDIATE` и выполняет все операции без `await` между ними; при любой ошибке откатывает всю транзакцию. D1 adapter использует native `batch` и не имитирует транзакцию последовательными независимыми запросами. Общий handler не импортирует Node SQLite в Worker.

API, CLI migration и recovery используют lock-файл рядом с локальной базой. Recovery требует остановленного API. Если процесс аварийно завершился и оставил stale lock, оператор сначала убеждается, что процесс из файла уже не работает, затем удаляет stale lock. Сам CLI не снимает чужую блокировку автоматически. Для замены существующей базы требуется явный `--force`; по умолчанию восстановление принимает новый путь.

Backup выполняется SQLite online backup API, поэтому включает уже закоммиченные данные из WAL и может сниматься при работающем API. Копия проверяется через `integrity_check`, `foreign_key_check` и наличие основных таблиц PITON; затем публикуется целиком и не перезаписывает существующий файл. Recovery сначала проверяет snapshot, создаёт независимую копию и заменяет целевой файл под эксклюзивной прикладной блокировкой. База и backup имеют режим файла `0600`; это контроль доступа ОС, а не шифрование содержимого. Полная копия содержит приватные работы и хеши учётных данных.

API не задаёт CSP, ограничивающую загрузку Pyodide/iframe; она остаётся задачей общей страницы и хостинга. Эта документация не утверждает, что локальный backup CLI обслуживает hosted D1: для D1 используется механизм резервирования инфраструктуры хостинга.

## Проверка

`tests/api.test.ts` проверяет 20 сценариев через реальный Node SQLite и Web `Request`, включая локальный/внешний auth boundary, Origin/CSRF, изоляцию трёх гостевых профилей, повышение гостя, конкурентные регистрации, ошибочные и повторные submissions, уникальность XP между режимами, prerequisites и демонстрационный `for`, приватные детали мира и навыка, отложенное повторение, все 12 канонических наград из фактических данных, CAS черновиков, последние 10 ревизий и восстановление, tutor fallback/consent/history, приватный экспорт, каскад удаления, конкурентное сохранение последнего профиля, атомарность SQL-порта и реальный backup/recovery.

```bash
node --import tsx --test tests/api.test.ts
```

Тесты API конструируют браузерное свидетельство для проверки доменных правил и не подменяют runtime-тесты Python. Реальные curriculum/runtime проверки находятся в соседних тестах. Hosted аутентификация, D1 инфраструктура и поведение cookie в preview дополнительно проверяются при интеграции сайта.
